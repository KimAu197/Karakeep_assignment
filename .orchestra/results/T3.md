## How the merge works
- **Inputs.** `recordBookmarkHistory` diffs stored against written values with the T1 `diffBookmarkHistory`. Every save, from `updateBookmark` or re-save, generates one `changeId` (`randomUUID()`) and one `createdAt` (`new Date()`).
- **Lookup.** For each changed field, inside the same transaction, it reads that bookmark's latest history row for that field: `ORDER BY createdAt DESC, rowid DESC LIMIT 1`. It does not filter by user.
- **When a change merges.** `mergeBookmarkHistoryChange` merges only if all of these hold:
  - the field's registry entry has `autosaved: true` (only `note`);
  - that latest row exists;
  - the row's `userId` equals the saving user;
  - `now - row.createdAt < 5 min`. Exactly 5 minutes does not merge.
- **What a merge does.** The old row is deleted, and the change becomes `{ oldValue: oldRow.oldValue, newValue: this save's newValue }`. If the two are equal under the empty-value rule (null, "" and undefined count as the same), no row is written at all. That covers a reverted edit.
- **What the new row gets.** A merged row is inserted with this save's `changeId` and `createdAt`, together with any other rows of this save. The earlier save's rows for other fields (for example its `title` row) are left untouched; they keep their own `changeId`.
- **Other fields and privacy.** Fields that are not autosaved always produce their own rows. Read-side privacy is unchanged: a merged row is still a `note` row, so collaborators never see it (tested).

## How the re-save capture is atomic
The stored-value read, the `bookmarks` update and the history delete/insert all run in one synchronous `ctx.db.transaction(..., { behavior: "immediate" })`. The test "does not change the bookmark when recording its history fails" drops the `bookmarkHistory` table in the in-memory test DB, then re-saves with a new title. The call rejects with `no such table: bookmarkHistory`, and the stored bookmark still has its original title and `archived: true`, so the update (which would have set the title and un-archived it) was rolled back.

## Could not do / limits
- **Decision 12 has no automated test.** The test DB is one in-memory connection, so a SQLITE_BUSY race with a second process cannot be reproduced there. It is checked by code reading only. Both transactions pass `{ behavior: "immediate" }`, the same precedent as `createBookmark` and `users.ts`.
- **Cost per save.** Each changed field now costs one extra indexed SELECT for the merge lookup. I do this for every changed field, not only autosaved ones, so the rule lives in one place: the pure function. That is at most 5 small queries per save.
- **No HTTP check on the running app.** That is V2's job, so no throwaway users were created.
- **Merging assumes the previous row is current.** If `note` were changed by a path that records no history between two autosaves, the merged row's `oldValue` would come from the older row. That path does not exist today, because both user write paths now record history.
