# T4 result: Edit dialog sends `title` only when it was changed (decision 13)

## Finding confirmed
In `apps/web/components/dashboard/bookmarks/EditBookmarkDialog.tsx` (as committed in f14014f):
- The form defaults include `title: getBookmarkTitle(bookmark)` (line 94). That returns `bookmark.title` if one is set. Otherwise it falls back to the link's crawled `content.title`, then the URL, or the asset's `fileName`.
- `onSubmit` always sent `title: values.title ?? null`.
- So opening Edit on a link with no stored title and saving without edits wrote the fallback title. The server then recorded "Title: empty -> crawled title". Server side: `updateBookmark` sets the title only when `input.title !== undefined` (packages/trpc/routers/bookmarks.ts ~line 720). Leaving the key out therefore keeps the stored title untouched.

## How "changed" is determined and how it behaves across resets
- It uses react-hook-form's own dirty tracking, `form.getFieldState("title").isDirty`. A field is dirty when its current value differs (deepEqual) from the form's current default values.
- I deliberately used `getFieldState` rather than `form.formState.dirtyFields.title`. `getFieldState` without a second argument reads the control's live `_formState`. `form.formState` is the snapshot from the last root render, and the root is not subscribed to `dirtyFields` here. I saw this in practice: a first test version using `formState.dirtyFields` failed because the value was stale.
- In RHF 7.62, `_formState.dirtyFields` is updated on every input change whether or not anything is subscribed (`updateTouchAndDirty` in `node_modules/react-hook-form/dist/index.esm.mjs`).
- How the existing resets interact with it:
  - **Dialog opens** (`useDialogFormReset`, only on the closed -> open transition): `form.reset(bookmarkToDefault(bookmark))` replaces the defaults and clears dirty fields. So "changed" is measured against what the dialog showed when it opened.
  - **Tag updates while open:** the `bookmark` prop changes, but the hook does not reset. The defaults stay the ones from opening, so a title edit stays dirty and an untouched title stays clean.
  - **After a successful save:** `form.reset(bookmarkToDefault(updatedBookmark))` sets the new defaults and clears dirty fields. Reopening resets again.
  - **Typed and then reverted** to exactly the pre-filled text: not dirty, so not sent. The stored title stays as it is, and the display is the same.
  - **Cleared input:** `""` differs from the default (text or fallback, or `null` for a text bookmark without a title), so it is dirty and sent as `""`, same as today.

## For the orchestrator
1. Other dialog fields are still always sent, by design (decision 13 says "other fields keep their behaviour"). From reading the code they do not create spurious history rows:
   - `url` is sent unchanged;
   - `description` is pre-filled `?? ""`, and the server treats `""` and `null` as the same;
   - `note` is `undefined` when null, so it is not sent;
   - `summary`, `author`, `publisher` and dates are not tracked.
   A V2 HTTP or browser check of "open Edit, Save without edits -> no new history entry" is still worth doing.
2. Typing a title and then reverting to the exact pre-filled fallback text counts as "unchanged", so it is not sent. I think this is correct, but it means a user cannot "pin" the crawled title as a stored title by retyping it identically.
