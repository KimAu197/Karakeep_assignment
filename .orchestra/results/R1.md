## Should-fix

### S1. Note autosave floods the history, and the 100-row cap then hides older changes (confirmed by reading)
- `apps/web/components/dashboard/preview/useNoteDraft.ts:9,104` saves the note 800 ms after typing stops. Each save goes through `updateBookmark`, and `packages/trpc/routers/bookmarks.ts:754-775` records a `note` row for every save that changes the note.
- Scenario: the owner types a 2-paragraph note with ~40 short pauses, which gives ~40 `note` rows ("My no" -> "My note is" -> ...). After two or three notes like this, the `LIMIT 100` (`bookmarks.ts:1122`) pushes earlier title/url/description changes out of `getBookmarkHistory`, and the sidebar mostly shows partial note drafts.
- The capture is correct under decision 4 (the DB really changed each time). The problem is that it makes the feature much less useful.
- Direction: coalesce consecutive saves of the same field by the same user within a short window, or exclude autosaves from history; at minimum, document it.

### S2. Saving the Edit dialog with no changes records a "Title: empty -> <crawled title / URL>" row (confirmed by reading)
- `apps/web/components/dashboard/bookmarks/EditBookmarkDialog.tsx:93` defaults the title field to `getBookmarkTitle(bookmark)`. For a link bookmark that is `content.title ?? content.url` whenever `bookmarks.title` is null (`packages/shared/utils/bookmarkUtils.ts:103-117`). `onSubmit` (line 145) always sends `title`, and Save is enabled without changes.
- Scenario: link bookmark, never renamed (`bookmarks.title` null, crawled title "Example Domain"). Open Edit, change nothing (or change only the description), Save. The history gets `title: null -> "Example Domain"`. The user sees a title change they did not make. The same happens for asset bookmarks (falls back to `fileName`).
- The write itself is pre-existing behaviour, and the row matches the DB. But from the user's point of view this is a no-op save that records something (AC2 intent).
- This dialog is the only title-edit path in the web preview, so the case will be common.
- Direction: document it, or make the dialog send `title` only when the field is dirty. That file is outside T1/T2 ownership.

### S3. A real user change of `title` / `note` is missed: the `createBookmark` re-save path (confirmed by reading)
- `packages/trpc/routers/bookmarks.ts:~305-330`: when a link with the same URL already exists (and the source is not exempt), `createBookmark` overwrites `title` and `note` on the existing bookmark if they were supplied. It writes no history.
- The browser extension always supplies `title: currentTab.title` (`apps/browser-extension/src/SavePage.tsx:108,156`).
- Scenario: the owner renames a bookmark in the web app to "My title" (a history row is recorded). Later they click the extension on the same page. The title is silently reset to the tab title, and the history still shows "My title" as the latest value, so it no longer agrees with the stored data.
- The context.md statement "All user edits of a bookmark go through `updateBookmark`" is therefore incomplete.
- Direction: record history in the re-save branch too, or list it explicitly as a known gap (decision 9).

## Minor

### M1. The same-millisecond ordering test does not prove the `rowid` tie-break (confirmed by experiment)
- `bookmarks.test.ts` "returns history newest first, even for saves in the same millisecond" would still pass if `desc(sql\`rowid\`)` were removed.
- The reason: SQLite answers `WHERE bookmarkId=? ORDER BY createdAt DESC` by scanning `bookmarkHistory_bookmarkId_createdAt_idx` backwards, and index entries end with the rowid, so ties already come out in rowid-descending order.
- Scratch run on the same schema with ids chosen so that PK order differs from insert order:
  `no tiebreak: ['D->E','C->D','note','B->C','A->B']` (plan `SEARCH h USING INDEX hi (bookmarkId=?)`), and the same output with the tie-break.
- The tie-break itself is sound: the table has a non-INTEGER text PK, so it is an ordinary rowid table, and a new rowid is max+1. It is just untested.
- Direction: none needed for correctness. If the test should guard it, make the planner unable to rely on the index (hard), or accept it as documentation.

### M2. The transaction now starts with a read: possible new SQLITE_BUSY under cross-process writes (suspicion, not reproduced)
- `bookmarks.ts:609-624`: the drizzle better-sqlite3 transaction is DEFERRED. Before this change, the first statement in `updateBookmark` was always a write, which waits on `busy_timeout`. Now it is a `SELECT`, so the transaction holds a read snapshot and then upgrades.
- In WAL mode, if the workers process commits a write between that SELECT and the first UPDATE, SQLite returns SQLITE_BUSY_SNAPSHOT immediately, without the busy handler, and the update fails with a 500.
- The window is microseconds because the code is synchronous, so this is very unlikely.
- Direction: `ctx.db.transaction(fn, { behavior: "immediate" })`.

### M3. Ordering is primarily by wall-clock `createdAt` (suspicion, theoretical)
- `bookmarks.ts:1121`: if the server clock steps backwards (NTP), a later save gets a smaller `createdAt` and is listed after an earlier save. That breaks the contract's "rows of a later save always come before rows of an earlier save".
- `rowid DESC` alone would be monotonic in insert order. There is no VACUUM anywhere in the repo, which might renumber rowids of a non-INTEGER-PK table.
- Direction: order by `rowid DESC` only, or accept and document.

### M4. No index on `bookmarkHistory.userId` despite the FK with `ON DELETE CASCADE` (read only)
- `packages/db/schema.ts:475-488`. When a user is deleted, SQLite must find child rows by `userId`, which means a full scan of `bookmarkHistory`. The neighbouring `highlights` table indexes `userId` (`schema.ts:448`).
- This matches the CONTRACT (which lists one index), so it is a performance note only.

### M5. The 100-row cap can split a save, and the header count is not the total (read only)
- `LIMIT 100` on rows (not saves) can drop part of the oldest save shown.
- `HistoryBox.tsx:152` shows `changes.length`, the number of saves within the newest 100 rows, with no "100+" or "older entries hidden" hint.

### M6. Frontend details (read only)
- `HistoryBox.tsx:110` is collapsed by default, unlike `HighlightsBox` (open by default). After an edit only the count changes. AC6 still holds, but the entry is not visible until the user expands the section.
- `HistoryBox.tsx:57-63`: `line-clamp-3` truncation has no way to see the full value (no expand control, no `title`).
- `HistoryBox.tsx:49`: a whitespace-only text (for example `text: "  "`, which is truthy, so it is written and recorded) renders as blank space rather than the "empty" label.
- Field labels "Text" (Note-item content) and "Note" (the private personal note) may confuse users, because the UI calls text bookmarks "Notes".
- User text is rendered as React text children (escaped). No `dangerouslySetInnerHTML`, so this is safe.
- Grouping keeps the server order, and the rows of a save are contiguous (same `createdAt`, consecutive rowids), so grouping is correct.

### M7. Test gaps relative to plan T1 step 6 and the ACs (read only)
- Only one BAD_REQUEST path is tested (url on a text bookmark). Text on a link bookmark and assetContent on a non-asset bookmark are not tested.
  - This does not matter today: every throw happens before the history insert, so atomicity is structural, and the AC5 test could not distinguish "insert inside the tx" from "insert after".
- The no-op test's `modifiedAt` assertion (`toBeGreaterThan(0)`) is satisfied by the later `archived`/`favourited` save, so it does not show that a same-value save bumps `modifiedAt`. Note also that the "No fields at all" save does not bump `modifiedAt`, despite the comment "A no-op save still bumps modifiedAt".
- Not tested:
  - an API key with only `bookmarks:read` reading history (should succeed via `createScopedAuthedProcedure`, query = read);
  - access lost after the bookmark is removed from the shared list (should be NOT_FOUND);
  - the 100-row cap;
  - title change on an asset bookmark.
- All step-6 items that the plan lists explicitly ARE covered: each field changed, one shared `changeId`, same value, no fields, `null`/`""`, url whitespace, untracked fields only, failed update, order, delete cascade, owner/collaborator/stranger, a non-owner cannot create history.

### M8. Collaborators see pre-sharing history of non-private fields (by design, worth documenting)
- Decision 8 marks only `note` as private. A collaborator added to a list today can read every old title, url, description and Note-item text the owner had before sharing (for example a title the owner deliberately renamed).
- No code defect. This is a privacy property to state in the write-up.

### M9. Small robustness / complexity points (read only)
- `bookmarks.ts:754`: `storedHistoryValues ?? {}` hides the "row vanished" case. If the bookmark is deleted concurrently, a title-only update now fails with an FK error (500) at the history insert instead of NOT_FOUND at the refetch.
- `bookmarks.ts:760`: the diff repeats the write condition for `text` (`input.text ? input.text : undefined`) instead of sharing a variable with the write at line 669. Correct today, but the two can drift apart.
- The read-before-write (a three-table join) runs on every `updateBookmark`, including archive/favourite toggles and bulk actions that touch no tracked field. The cost is negligible.

## Checked and found correct

- **Capture.** Every recorded field is written, and every write is recorded:
  - `title` and `note`: written via `commonUpdateData` (the bookmarks update always runs when they are present, and ownership guarantees the `userId` match).
  - `url` and `description`: written via `linkUpdateData` (a zero-row result throws, so there is no row without a write). `url` is diffed trimmed, and is skipped when falsy, exactly as it is written.
  - `text`: diffed only when truthy, exactly as written.
  - `null` (via `.nullish()`), `undefined` and `""` are normalised to "empty", per decision 4.
- **Atomicity.** The read and the inserts are inside the same synchronous transaction. All BAD_REQUEST throws precede the insert, and any throw rolls everything back.
- **Ids and time.** One `changeId` and one `createdAt` per save.
- **Authorization.**
  - `getBookmarkHistory` uses `bookmarksProcedure` (API-key scope `bookmarks:read` for a query) plus `ensureBookmarkAccess`. Strangers and ex-collaborators get NOT_FOUND "Bookmark not found".
  - Private rows are filtered in SQL before the LIMIT, using the registry-derived `PRIVATE_BOOKMARK_HISTORY_FIELDS`.
  - `isOwner` compares against the bookmark's `userId`.
  - Nothing new is exposed in the update response or in error messages.
- **Schema and migration.** They match the CONTRACT. Both FKs cascade, and `createdAt` is `timestamp_ms`. No `relations` were added, which is consistent with `highlights` (that table has none either).
- **Shared hook.** The one added `invalidateQueries` is harmless for mobile and the extension (it is client-side only, and they share the `AppRouter` type). shared-react typechecks.
- **i18n.** `preview.history.*` resolves in the English file. No other locales were touched (`en` is the fallback).
