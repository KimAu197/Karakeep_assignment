  The task: item change history

⏺ Your picture has the two visible ends right, but the most important part is
  the piece between them: the capture step inside updateBookmark
  (packages/trpc/routers/bookmarks.ts:581-770). The table and the sidebar are
  routine; every hard requirement in the brief (no-op edits, old vs new values,
  failed writes, concurrent edits) is decided in that one function.

  How the pipeline changes

  Write path (existing function, two steps added inside the transaction):

  validate input → ownership check → BEGIN transaction
      + read the current stored values          (new)
      + compare with the incoming values        (new)
        write type table (link / text)          (as today)
        write bookmarks table                   (as today)
      + insert one history row per changed field (new)
  COMMIT → re-read bookmark → queue search reindex + webhook → return

  Read path (all new, but copies getBookmark's shape):

  History section in sidebar → bookmarks.getBookmarkHistory
      → ensureBookmarkAccess (owner, or viewer of a shared list)
      → select rows for this bookmark, newest first
      → drop private-field rows if the caller is not the owner

  One small change joins them: useUpdateBookmark
  (packages/shared-react/hooks/bookmarks.ts:103) already invalidates the cached
  bookmark after a save, and it needs to invalidate the history query too so the
  sidebar updates without a reload.

  Implementation ideas

  1. One field registry drives everything. Keep a single list of tracked fields,
     each tagged with where it lives and whether it is private:

  // sketch
  const TRACKED = [
    { field: "title",       private: false },
    { field: "url",         private: false },
    { field: "description", private: false },
    { field: "text",        private: false },  // content of a Note item
    { field: "note",        private: true  },  // owner's personal note
  ] as const;

     The diff loops over it, and the read query filters with it. The privacy
     rule then lives in one place rather than being repeated in the write and
     read code.
  2. Make the diff a pure function. diffBookmark(before, incoming) → [{ field, 
     oldValue, newValue }], with no database access. That makes the no-op rule
     testable in isolation: a field that was not sent, or was sent with the
     stored value, yields nothing. It should compare the value that will
     actually be written (the URL is trimmed at line 599), and treat null and ""
     as equal.
  3. Table: one row per changed field. Columns are id, bookmarkId (deleted with
     the bookmark), userId, field, oldValue, newValue and createdAt, with an
     index on (bookmarkId, createdAt). All rows from one save share one
     timestamp, so the UI can group "title and URL changed" as a single edit.
  4. Reads happen inside the transaction. The transaction callback is
     synchronous, so nothing in the same server process can run between reading
     the old value and writing the new one. That is the answer to "concurrent
     updates". Because the history insert is in the same transaction, a failed
     write rolls both back, which answers "failed writes".
  5. Leave the existing writes alone. Today a no-op save still bumps modifiedAt.
     I would not change that; I would only skip the history rows. Altering
     existing behaviour risks breaking the current tests for no benefit to the
     task.
  6. UI: a HistoryBox next to HighlightsBox in
     apps/web/components/dashboard/preview/, placed in the sidebar block at
     BookmarkPreview.tsx:502-537. Each entry shows the field, old → new (long
     text truncated), and a relative time.
  7. Tests where the risk is. In bookmarks.test.ts: an edit creates a row with
     the right old and new values, a no-op creates none, and order is newest
     first. In sharedLists.test.ts, which already sets up an owner and a
     collaborator: the collaborator sees title history but not note history, and
     a stranger gets "not found".

  Build order

  I would build a thin slice first: the table, capture for title only, the
  query, and the sidebar section, then prove it in the browser. Widening to more
  fields afterwards is just adding lines to the registry.

  What this leaves out

  - Background writes: the crawler and the AI summariser write some of the same
    columns directly, so they bypass history.
  - Tags: they have their own mutation and are not covered.
  - Production concerns: pagination and retention of old history are not
    addressed.

  - Which fields to track. I'd take the five in the sketch, which includes one

  - Whether to keep idea 5. That means leaving the existing no-op write

❯ explian Adds the "autosaved" flag for the personal note and the 5-minute      
  merge rule                                                                    

⏺ The problem it solves

  The personal note in the sidebar has no Save button. It saves by itself about
  0.8 seconds after you stop typing. Each of those saves is a real update, so
  before this fix each one became its own history entry.

  Typing "call Sam about the invoice" with two short pauses used to produce:

  Note:  call Sam              →  call Sam about the invoice
  Note:  call                  →  call Sam
  Note:  (empty)               →  call

  That is three entries for one thought, and none of the middle states matter to
  anyone. A long note could produce dozens and push real title or URL changes
  out of the 100-row list.

  The "autosaved" flag

  The registry is the single list of tracked fields. Each field already had a
  private flag; it now has a second one:

  title:       { private: false, autosaved: false },
  url:         { private: false, autosaved: false },
  description: { private: false, autosaved: false },
  text:        { private: false, autosaved: false },
  note:        { private: true,  autosaved: true  },

  The flag describes how the UI saves that field. Only the personal note saves
  while you type; the others are saved when you press a Save button, so each of
  their saves is a deliberate act.

  The merge rule

  When a save changes a field, the server looks at the most recent history entry
  for that same field on that bookmark. It merges the new change into that
  entry only if all three are true:

  1. The field is flagged autosaved.
  2. The earlier entry was written by the same user.
  3. The earlier entry is less than 5 minutes old.

  Merging means the earlier entry is removed and one new entry is written that
  runs from the earlier entry's old value to the new value, with the current
  time. The example above becomes:

  Note:  (empty)  →  call Sam about the invoice

  Three consequences

  - Type and undo leaves nothing. If you type something and delete it again
    within the window, the merged entry would read "empty → empty", so no entry
    is kept at all.
  - Titles are never merged. Two title edits ten seconds apart stay two entries,
    because title is not flagged. Each one was a deliberate save, and the demo
    still shows every edit.
  - A pause of five minutes starts a new entry. Come back to the note later and
    that edit is recorded separately from the first.

  The merge happens inside the same database transaction as the note save
  itself, so the note and its history cannot get out of step.

  One trade-off to be able to explain: within the 5-minute window, the
  intermediate drafts of a note are not kept. History shows where the note
  started and where it ended.

❯ so it means only 5 minute the notes will show in the history?                 

⏺ No. Note history is kept permanently, the same as title or URL history. An
  entry stays until the bookmark itself is deleted.

  The 5 minutes only decides how saves are grouped into entries. Because the
  note saves itself every time you pause typing, the rule is: saves that happen
  close together count as one edit, and a save that comes after a gap of 5
  minutes or more starts a new entry.

  An example over one day:

  ┌──────────┬───────────────────┬──────────────────────────────────────────┐
  │   Time   │    What you do    │            History afterwards            │
  ├──────────┼───────────────────┼──────────────────────────────────────────┤
  │ 10:00:00 │ Type "call Sam"   │ Entry 1: empty → "call Sam"              │
  ├──────────┼───────────────────┼──────────────────────────────────────────┤
  │ 10:00:20 │ Add " about the   │ Entry 1 becomes: empty → "call Sam about │
  │          │ invoice"          │  the invoice"                            │
  ├──────────┼───────────────────┼──────────────────────────────────────────┤
  │ 10:01:10 │ Add " on Friday"  │ Entry 1 becomes: empty → "call Sam about │
  │          │                   │  the invoice on Friday"                  │
  ├──────────┼───────────────────┼──────────────────────────────────────────┤
  │ 15:30:00 │ Change "Friday"   │ Entry 2 is added: "…on Friday" → "…on    │
  │          │ to "Monday"       │ Monday". Entry 1 stays as it was         │
  ├──────────┼───────────────────┼──────────────────────────────────────────┤
  │ Next     │ Open the bookmark │ Both entries are still there             │
  │ week     │                   │                                          │
  └──────────┴───────────────────┴──────────────────────────────────────────┘

  So at 10:00 you get one entry for the whole burst of typing rather than three,
  and the afternoon edit is recorded separately because more than 5 minutes had
  passed.

  What you do lose is the in-between drafts inside a burst: history does not
  keep "call Sam" as its own step. There is one edge case on top of that. If you
  type something and delete it again within the 5 minutes, the note ends where
  it started, so no entry is kept for it.
