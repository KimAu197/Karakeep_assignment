# T5 result: skip history when the bookmark vanished before the write (decision 15)

Status: DONE. Nothing was committed, and git state was not touched. No schema change and no migration.

## What I did
- **Confirmed the finding.**
  - Bug: `readBookmarkHistoryValues` returned `{}` when the bookmark row was missing (`.get() ?? {}`). A save with a title or note therefore diffed against "all empty" and inserted history rows for a bookmark id that no longer existed, which failed with `FOREIGN KEY constraint failed`.
  - Reproduced: I wrote the new tests first and ran them against 722fb53. Both entry points failed with `TRPCError: FOREIGN KEY constraint failed` (`SQLITE_CONSTRAINT_FOREIGNKEY`).
- **Fix (one file, two small changes in `packages/trpc/routers/bookmarks.ts`).**
  - `readBookmarkHistoryValues` now returns `BookmarkHistoryValues | undefined`: the `?? {}` is gone, so a missing row gives `undefined`.
  - `recordBookmarkHistory` takes `stored: BookmarkHistoryValues | undefined` and returns early when it is `undefined`, writing no history.
  - Nothing else changed: no change in either caller, the transactions, or any other behaviour. Most of the diff in the read helper is the formatter re-indenting it after the wrapping parentheses were removed.
- **"Row missing" vs "fields null".** The read is `bookmarks LEFT JOIN bookmarkLinks LEFT JOIN bookmarkTexts`. When the bookmark exists but has no link or text row (an asset bookmark), `.get()` still returns an object whose `url`, `description` and `text` are null. It returns `undefined` only when the `bookmarks` row itself is gone. A test pins the asset case.

## Test seam
The helper `deleteBookmarkBeforeNextTransaction(db, id)` in the test file spies on the test database's `transaction` with `vi.spyOn(db, "transaction").mockImplementationOnce(...)`. That one call deletes the bookmark row (cascading to its link row), then calls through to the real `transaction` with the same callback and config.
- The same `db` object is the request's `ctx.db`.
- Neither entry point opens another transaction before the capture one: `attemptToDedupLink` and `ensureBookmarkOwnership` only read.
- So the row disappears exactly between the earlier check and the capture transaction, and no production code changed for the test.

**(a) Re-save through `createBookmark`, with a title (and note) supplied.**

  - `id` = the deleted bookmark's id;
  - `alreadyExists: true`, `archived: false`;

- It also asserts that `triggerSearchReindex` was called with `(id, { groupId: userId })`, the bookmark row is gone, and the `bookmarkHistory` table is empty.

**(b) `updateBookmark` with a title (and note).**
- At 28ae675 the transaction had no read. With only `title` or `note` sent, the `bookmarks` UPDATE matches zero rows without error. The refetch `Bookmark.fromId` then throws `TRPCError { code: "NOT_FOUND", message: "Bookmark not found" }`.
- The test asserts the call **rejects** with `{ code: "NOT_FOUND", message: "Bookmark not found" }` and that the history table is empty.
- If link, text or asset fields are also sent, the existing zero-row checks still throw `BAD_REQUEST` first, exactly as at 28ae675. That path is unchanged and not newly tested.

**(c) Guard for the normal case.**
- An asset bookmark (no link or text row) updated with a title and note records both rows (`title null -> "Asset title"`, `note null -> "Asset note"`).
- This passes both before and after the fix. It protects against a fix that confuses "row missing" with "fields null".

## Could not do / limits
- **Pre-feature behaviour was established by reading, not running.** Running 28ae675 would have needed a second checkout and install; a git worktree would change git state. The relevant code paths are short and are quoted above.
- **The window is only closed at the start of the capture transaction.** The row can still vanish between `ensureBookmarkOwnership` and the transaction; that is the case handled here. Inside the transaction, `{ behavior: "immediate" }` holds the write lock, so it cannot vanish between the read and the insert.
