## How the diff and capture work
- **Diff.** `diffBookmarkHistory(stored, toWrite)` is pure. It walks `BOOKMARK_HISTORY_FIELDS` in registry order and skips every field that is `undefined` in `toWrite`, meaning not written. It normalises `null`, `undefined` and `""` to `null`, so all three count as "empty". It emits `{ field, oldValue, newValue }` only when the normalised values differ, and stores empty values as `null`.
- **Capture.** At the start of the existing synchronous `ctx.db.transaction`, `updateBookmark` reads `title` and `note` from `bookmarks`, `url` and `description` from `bookmarkLinks`, and `text` from `bookmarkTexts` in one LEFT JOIN query. At the end of the same transaction, after all existing writes, it diffs against the values that were actually written:
  - `title` and `note` from `commonUpdateData`;
  - `url` (trimmed) and `description` from `linkUpdateData`;
  - `text` only when `input.text` is truthy.
  If anything changed, it inserts one row per field, all sharing one `changeId` (`crypto.randomUUID()`) and one `createdAt` (`new Date()`, millisecond precision). Any `BAD_REQUEST` throw happens before the insert, so the transaction rolls back and no history survives. The existing write logic is untouched: a no-op save still bumps `modifiedAt` (a test covers this), and the errors are unchanged.
- **Read.** `getBookmarkHistory` is guarded by `ensureBookmarkAccess`, so strangers get NOT_FOUND. For a non-owner, it filters private fields in SQL (`field NOT IN PRIVATE_BOOKMARK_HISTORY_FIELDS`). Doing this before `LIMIT 100` means a collaborator still gets up to 100 visible rows.
- **Ordering.** Rows are ordered `createdAt DESC, rowid DESC`, limit 100. The table has a text primary key, so it is an ordinary rowid table. Without AUTOINCREMENT, SQLite gives each new row `max(rowid)+1`, which is larger than every row already present. So when two saves share a millisecond, the later save's rows still come first; a test pins this using fake `Date`. Within one save, rows come in reverse registry order (note, text, description, url, title). The UI groups by `changeId`.

## Not done / limits
- I did no HTTP smoke test against the running app; V1 owns that. No throwaway users were created.
- I added no Drizzle `relations` for the new table. Its model, `highlights`, has none either, and the query uses the select builder, so relations are not needed.
- There is no separate index on `bookmarkHistory.userId`. The CONTRACT specifies only (bookmarkId, createdAt). Deleting a user therefore scans this table once for the FK cascade check. That is fine for v1.
- If the system clock goes backwards between two saves, `createdAt` ordering wins over `rowid`. This is a theoretical edge case only.
