# T6 result: Edit dialog sends `note` only when it was changed (decision 14)

## What I did
- The helper `withTitleOnlyIfChanged` became **`withTitleAndNoteOnlyIfChanged(values, { title, note })`**. I renamed it because the old name would mislead now that it covers two fields.
  - Title not changed: the payload has no `title` key. Changed: `title: values.title ?? null`, as in T4.
  - Note not changed: the payload has no `note` key. Changed: `note` is sent as typed, the same value that was always sent before. A cleared note is sent as `""`.
  - All other fields are spread through unchanged.
- In `EditBookmarkDialog.tsx`, `onSubmit` passes `{ title: form.getFieldState("title").isDirty, note: form.getFieldState("note").isDirty }`. This is the same dirty-state source as T4: it reads RHF's live control state, not a possibly stale `form.formState` render. The reset behaviour is the same as for the title:
  - "changed" is measured against the values set when the dialog opened, or after a save;
  - tag updates while open do not reset the form;
  - changing a field and then reverting to the exact original counts as unchanged.
- Clearing value: the update schema has `note: z.string().optional()`, so `""` validates. The server does `if (input.note !== undefined) commonUpdateData.note = input.note` (packages/trpc/routers/bookmarks.ts ~line 841), so `""` is stored and clears the note. This is unchanged from before; the dialog has always sent `""` for an emptied textarea. If no note is stored, the default is `undefined`. Typing and then deleting gives `""`, which is dirty, so `""` is sent. History treats `""` and `null` as equal, so no row is recorded.

## Stale-note mechanism: what reading the code shows
**Confirmed by reading:**
- The dialog's form state is filled only on the closed -> open transition (`useDialogFormReset`), from the `bookmark` prop. In the preview that prop is the cached `getBookmark` query result, passed through `ActionBar`.
- The note default is `bookmark.note` (or `undefined` when null).
- Before this change, `onSubmit` always sent `note`.
- So whatever note the cache held when the dialog opened was written back on any save. A newer note saved from the sidebar after that point would be overwritten.

**Not confirmed:** the reviewer's exact sequence in the common mouse path. Existing code already narrows it:
- clicking Edit blurs the sidebar textarea, and `onBlur={flush}` sends the pending note immediately;
- `useNoteDraft`'s `onMutate` writes the new note into the `getBookmark` cache optimistically. TanStack's `execute` runs `onMutate` even when the mutation is queued behind an earlier save in the same `scope` (`node_modules/@tanstack/query-core/build/modern/mutation.js` lines 89-100);
- `ActionBar` opens the dialog in a `setTimeout` so that the cache update reaches the component first. Its comment says exactly this.

**Remaining windows I can see by reading (not reproduced):**
- A `getBookmark` refetch already in flight (e.g. from an earlier save's invalidation) lands after the optimistic update and puts the old note back in the cache before the dialog opens.
- After a failed autosave, `onError` invalidates the query, so the cache holds the server's old note while the sidebar keeps the unsent text.
- Timing of the React render versus the `setTimeout` is not guaranteed.

Either way, with this change a dialog save can no longer write a note the user did not touch in the dialog, whatever the cache held.
