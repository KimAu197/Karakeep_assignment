## Minor

### M1. (Suspicion, not reproduced in a browser) A stale note sent by the Edit dialog can silently revert an autosaved note, and the merge rule then erases both history entries
- `EditBookmarkDialog.tsx` line 94 (`note` default) + `useDialogFormReset` (resets only when the dialog opens) + `ActionBar.tsx` line 72 (opens the dialog from the preview, where the sidebar note editor lives) + `useUpdateBookmark` (no optimistic cache update).
- Scenario:
  1. The stored note is "A". In the preview sidebar the user types "B". Clicking Edit blurs the field, which flushes the autosave.
  2. The dialog opens on the next tick with the not-yet-refetched prop, so the note default is still "A".
  3. The user changes the title and saves. The dialog always sends `note: "A"`.
  4. The server writes B -> A. The merge sees the A->B row from the same user under 5 minutes old, treats this as a revert, deletes that row and writes nothing.
- Result: the note silently loses "B", and the history shows no note activity at all. Without the merge rule, history would at least show A->B and B->A.
- The overwrite itself predates the feature, and decision 13 keeps the other fields' behaviour. The new part is that the merge hides it.
- Direction: send `note` only when dirty too (the same helper generalises), or record this as a known limit.

### M2. Re-save can now throw on a delete race where it used to silently succeed
- `bookmarks.ts` re-save transaction (~lines 428-451) and `readBookmarkHistoryValues` (`?? {}`).
- Scenario: the bookmark is deleted between `attemptToDedupLink` and the transaction, and the caller supplies a title or note. The stored values come back `{}`, the UPDATE matches 0 rows, and the history INSERT violates the `bookmarkId` FK (production sets `foreign_keys = ON`). The result is a 500 instead of a "successful" no-op.
- updateBookmark has had the same edge since f14014f.
- Read only, not reproduced (tests use an in-memory DB without `foreign_keys` set).
- Direction: skip recording when the stored read returns no row (or accept it as harmless).

### M3. The merge does not check that the previous row's `newValue` equals the currently stored value
- `lib/bookmarkHistory.ts` `mergeBookmarkHistoryChange`.
- If anything ever wrote `note` without recording history, the merged row would claim a transition that skips the unrecorded value.
- Today every note write is captured: updateBookmark, re-save, and the import source is exempt. I found no other writer by grep, so this is theoretical.
- Direction: none needed now. Optionally compare `previous.newValue` with `change.oldValue` before merging.

### M4. The merge lookup runs for non-autosaved fields too
- `recordBookmarkHistory` does one SELECT per changed field, including title/url/description/text, whose result is always ignored.
- Direction: check `BOOKMARK_HISTORY_FIELD_REGISTRY[field].autosaved` before querying.

### M5. No integration test for a revert inside a save that also changes another field
- The unit tests cover the merge function. The router test covers an earlier multi-field save whose note row is merged away. A save like `{ note: <revert>, title: "U" }` (note row deleted, title row written) is not exercised end to end.
- Reading the code, it is correct: per-change loop, then one insert.
- Direction: optional one-line test.

### Note (not a defect)
- The window slides: after a merge, the row's `createdAt` is the latest save, so a note edited for an hour with pauses under 5 minutes becomes one entry. This matches decision 10 as written ("most recent row ... less than 5 minutes before now").

## Checked and found correct

- **Decision 10:**
  - The registry has `autosaved` on `note` only.
  - Window check: `now - previous.createdAt >= WINDOW` means no merge, so a merge happens only when the gap is strictly less than 5 minutes.
  - Same-user check is present.
  - The latest row of the same field on the same bookmark is used.
  - Only that row's id is deleted. Rows of other fields from the earlier save stay.
  - A revert under the empty-value rule writes nothing.
  - The merged row gets this save's `changeId`/`createdAt`, and a new rowid that is larger than every remaining row even after the delete, so ordering and the 100-row read stay deterministic.
  - Private-field filtering on read is unchanged, and merged rows keep `field = "note"`. A no-op save returns early and does not extend the window.
- **Decision 11:**
  - The `alreadyExists` branch is identical to f14014f except for the transaction wrapper: the exempt-source early return comes before it, and the `.set({...resaved, modifiedAt: now})`, the `where` (userId + id), reindex, webhook and the returned object are unchanged.
  - The read, update and insert are in one `immediate` transaction; the atomicity test (DROP TABLE) proves the update rolls back.
  - Only `input.title`/`input.note` are passed, and `undefined` means not recorded, which matches what `resaved` writes (including `title: null`).
  - The recorded user is `ctx.user.id`, the owner, because the dedup lookup is scoped to the caller.
- **Decision 12:**
  - `{ behavior: "immediate" }` matches the precedents (`users.ts:139`, `lists.ts:331/737`, `createBookmark` main path).
  - Drizzle's better-sqlite3 session maps it to `nativeTx.immediate()`. Both callbacks are synchronous.
  - No caller passes a transaction as `ctx.db` (grep). Inside a nested tx, drizzle would use a savepoint and ignore `behavior`, which is harmless.
- **updateBookmark:** `git diff -w` shows only the stored-value read moved into `readBookmarkHistoryValues` (same query, same `?? {}`) and the insert moved into `recordBookmarkHistory` (same written values). Every other branch is byte-identical.
- **Decision 13:**
  - `withTitleOnlyIfChanged(values, form.getFieldState("title").isDirty)` omits `title` when the field is not dirty relative to the last reset. The form is reset on open (`useDialogFormReset`), not on prop changes, and after a save.
  - Clearing a title is dirty and sends `""`, as before. Changing it back to the default is not dirty and is omitted, which is correct.
  - RHF 7.57 tracks `dirtyFields` even without a subscription (the jsdom test proves it), and the shadcn `FormField`/`useFormField` subscribes anyway.
  - The other tracked fields on an unedited save with a fresh prop:
    - `note`: null becomes `undefined`, so it is not sent; a string equals the stored value.
    - `description`: `?? ""` is equal to null under the empty rule.
    - `url`: the stored url; the schema has no transform.
    - `text`: not in the dialog.
  - So no history row results (see M1 for the stale-prop case).
- **modifiedAt test:** now accurate. A same-value save bumps it (the `bookmarks` update runs because `title` is set). A no-field save does not, because `Object.keys(commonUpdateData).length > 1 || somethingChanged` is false.
- **Tests vs a broken implementation:**
  - The boundary test hits exactly 5 minutes.
  - "merges only with the latest note row" would fail if the oldest row were picked.
  - The other-user test, the revert test, the non-autosaved-fields test and the AC10 cases (changed / same / absent / exempt / atomic) are all discriminating.
  - The gaps are S1 and M5.
